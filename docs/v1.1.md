# V1.1 — Mensagens, regras e links

## Configuracao multiguild

A estrutura atual e o procedimento de migracao estao em [Multiguild](multiguild.md).
O registro fica em `config/default.toml`, os defaults em `config/guilds/defaults/`
e as propriedades locais em `config/guilds/<name>/`. O formato antigo permanece
somente como compatibilidade temporaria, com precedencia documentada nesse guia.

## Permissões

Usuário: Gerenciar mensagens, além do cargo moderador configurado quando houver.
O dono do servidor dispensa a restrição pessoal. Administração precisa estar ativa.
O usuário autorizado não precisa poder enviar mensagens diretamente no destino.

Bot: Ver canal + Enviar mensagens; para embeds, também Inserir links (Embed Links).
Para recuperar/verificar mensagens existentes, Ler histórico de mensagens.
Gerenciar mensagens não é necessário para publicar, editar ou excluir mensagens
próprias. Gerenciar cargos continua obrigatório para `/role`, com hierarquia.
Sobrescritas específicas dos canais são calculadas pelo Serenity. Não use
Administrador como solução. Somente intent GUILDS; nenhuma intent privilegiada.

## Comandos e interface

| Comando | Operação |
|---|---|
| `/announce channel content` | Texto rápido com prévia; destino restrito ao canal configurado |
| `/announcements create` | Formulário de título, conteúdo, cor, imagem e rodapé |
| `/announcements edit id` | Edita anúncio gerenciado preservando a mensagem |
| `/announcements list` | Lista chaves de anúncios e IDs das mensagens |
| `/announcements delete id` | Prévia e confirmação de exclusão |
| `/rules preview`, `/links preview` | Prévia privada sem publicação |
| `/rules publish`, `/links publish` | Prévia e confirmação; publicação existente vira atualização |
| `/rules update`, `/links update` | Atualiza a mesma mensagem registrada |
| `/rules list`, `/links list` | Lista IDs e títulos |
| `/rules add id`, `/links add id` | Adiciona item por formulário; ID único informado no comando |
| `/rules edit id`, `/links edit id` | Edita item por formulário |
| `/rules remove id`, `/links remove id` | Remove item somente após confirmação na prévia |

Nas regras, `edit` e `remove` também aceitam número. Links usam ID simbólico.
As entradas possuem `order`; itens adicionados entram no fim. Templates podem
definir a ordem inicial. Links começam vazios, sem URLs sugeridas automaticamente.

O slash recebe confirmação efêmera imediatamente. Depois da autorização, o botão
**Preencher formulário** abre o modal nativo. Essa etapa evita perder o prazo de
3 segundos durante consultas de permissões. Há 90 segundos para abrir e 3 minutos
para preencher. A prévia dura 4 minutos; apenas o autor pode operar os botões.
**Editar** permite revisar antes de confirmar; em coleções, informe o ID do item.
**Salvar rascunho** persiste regras/links sem publicar. **Confirmar / Publicar**
persiste e envia ou atualiza. **Cancelar** não altera conteúdo nem publica.
Remoções de itens também passam por essa confirmação; exclusões de anúncios têm
botão explícito de exclusão. Uma prévia antiga é rejeitada após outra alteração.

As respostas administrativas são privadas e as mensagens publicadas desabilitam
menções automáticas. Texto, títulos, descrições, campos, rodapés, total de 6000
caracteres e máximo de 10 embeds são validados sem truncamento. Contagem UTF-16
é conservadora para emojis. Imagens e links aceitam somente HTTP/HTTPS sem credenciais.
O bot não baixa imagens nem faz requisições aos links; o Discord renderiza as URLs.

## Templates

Conteudos estaticos agora ficam em `config/guilds/defaults/` e
`config/guilds/<name>/`, nos arquivos `rules.toml`, `announcements.toml` e
`links.toml`. Sao carregados uma vez na inicializacao. Campos herdam os defaults;
listas especificas substituem integralmente as compartilhadas. Personalizacoes
JSON continuam prioritarias. Veja [Multiguild](multiguild.md#conteudos).

Regras visuais nao substituem Rules Screening/Onboarding do Discord.

## Persistência e recuperação

`DATA_DIR` tem padrão `data`. Cada servidor usa `data/guilds/GUILD_ID/state.json`.
O arquivo reúne `documents`, `publications`, `revision` e `pending`. Uma única
substituição atômica evita salvar documento e referência de mensagem separadamente.
O temporário é criado no mesmo diretório, sincronizado e substitui o arquivo final.
Um mutex serializa transações e efeitos HTTP; um lock de arquivo impede duas
instâncias de escrever no mesmo diretório. JSON inválido provoca erro, sem reset
silencioso. Dados reais e templates privados por servidor são ignorados pelo Git.

Publicações normais reutilizam o ID registrado. Antes de atualizar/excluir, o bot
consulta a mensagem e verifica sua autoria. Se ela foi apagada, remove a referência
obsoleta e pede uma nova prévia/confirmacão para republicar. Mudança do canal
configurado é bloqueada até revisão do registro, evitando migração silenciosa.

Não existe transação distribuída entre Discord e disco. Antes de chamar a API,
o bot grava `pending`. Se houver timeout, erro HTTP ou falha ao salvar o resultado,
novas publicações desse servidor ficam bloqueadas para evitar duplicação.
Recuperação: pare o bot, faça backup de `state.json`, confira no canal se a operação
ocorreu, corrija `documents`/`publications` com os IDs reais quando necessário,
incremente `revision`, defina `pending` como `null` e reinicie. Nunca limpe `pending`
sem conferir o Discord. Esse procedimento também serve para reconciliar um canal
alterado. Não edite JSON com o processo ativo. Preserve backup antes de intervenções.

## Docker

Compose monta `config` somente para leitura e usa o volume nomeado
`bot-data` em `/app/data`. A imagem cria esse diretório pertencendo ao UID 10001;
o volume novo herda a propriedade. Volumes previamente criados com outro dono
precisam de ajuste pelo operador. Não existem portas novas ou serviços adicionais.

```sh
docker compose config --quiet
docker compose up -d --build
docker compose logs -f bot
docker compose down
```

`down` preserva dados; **não use `down -v`** para operações normais. Faça backup do
volume com o bot parado. Para execução nativa: `cargo run --locked`.

## Homologação no Discord

1. Anúncios: retire Gerenciar mensagens do bot, permita Ver canal/Enviar mensagens,
   negue envio direto ao moderador no destino. Execute `/announce`; cancele uma
   prévia e confirme outra. Verifique ausência de notificações por menções.
2. Habilite Embed Links. Crie um anúncio por modal; edite a prévia, publique,
   consulte `list`, edite pelo ID e confira que não surgiu outra mensagem.
   Exclua com confirmação. Negue Send Messages/Embed Links e confirme rejeição.
3. Regras: `preview` deve mostrar dois embeds roxos com cinco regras cada. Publique,
   execute publish novamente e confirme que o ID é preservado. Edite uma regra,
   salve rascunho e depois atualize. Teste adicionar, remover e cancelar.
4. Links: adicione um ID com URL HTTP/HTTPS real escolhida por você. Salve rascunho,
   publique e edite. Rejeite URL inválida/ID duplicado. Remova e atualize a mensagem.
5. Reinicie o bot e atualize regras/links; os IDs devem continuar iguais. Apague
   uma mensagem manualmente e teste recuperação por nova publicação confirmada.
6. Teste usuário não autorizado, módulo desabilitado, outro servidor, dois admins
   editando ao mesmo tempo, expiração de sessão e dois cliques de confirmação.
7. Teste `/role add` e `/role remove` com cargo abaixo e acima do bot.

A suíte automatizada não se conecta ao Discord. Homologação de modals, componentes,
renderização e efeitos HTTP continua sendo feita no servidor de desenvolvimento.
# Estabilização e perfil

O [guia de estabilização](stabilization-profile.md) documenta autocomplete e IDs
aceitos em anúncios, reconciliação de mensagens excluídas, diagnóstico de registro,
os cinco comandos de perfil e o checklist atualizado de homologação.
Use `/announcements list` para obter a chave interna ou o Message ID aceito por
`edit/delete`. A edição preserva o Message ID; exclusão sempre pede confirmação.
